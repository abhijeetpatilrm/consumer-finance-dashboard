PHASE 2 — BACKEND APIs

Continue from the existing Phase 1 implementation. Inspect the current code first and preserve the established architecture, schema, seed pipeline, normalization logic, and tests.

Do NOT rebuild Phase 1.
Do NOT implement frontend UI in this phase.

Goal: implement production-quality backend APIs for transactions, analytics, and rewards.

==================================================
1. TRANSACTIONS API
==================================================

Implement:

GET /api/transactions
GET /api/transactions/{id}

GET /api/transactions must support server-side:

- page
- page_size
- search
- category
- status
- min_amount
- max_amount
- start_date
- end_date
- sort_by
- sort_order

Search should work against relevant transaction fields, especially merchant and transaction ID.

Use PostgreSQL queries rather than loading all 10,000 records into Python.

Return a consistent paginated response:

{
  "items": [...],
  "page": 1,
  "page_size": 25,
  "total": ...,
  "total_pages": ...
}

Validate query parameters and return proper HTTP errors.

Support sensible sorting fields such as:
- timestamp
- amount
- merchant
- category
- status

Prevent arbitrary SQL/order-by injection by using an explicit allowlist.

GET /api/transactions/{id} should return the complete transaction or 404.

==================================================
2. ANALYTICS APIs
==================================================

Implement:

GET /api/analytics/category
GET /api/analytics/monthly

Category analytics should return spending grouped by category.

Monthly analytics should return spending grouped by month.

Use PostgreSQL aggregation rather than fetching all transactions into application memory.

For spending analytics, clearly define/document which transaction statuses are included. Use the assignment's intended spending semantics consistently.

Handle Uncategorized correctly.

Return frontend-friendly JSON.

==================================================
3. REWARDS APIs
==================================================

Implement:

GET /api/rewards
GET /api/rewards/balance
POST /api/rewards/{reward_id}/redeem

Use the existing reward calculation/business-rule foundation from Phase 1.

Seed a sensible rewards catalogue if not already present.

Balance should be persisted in the database.

Redemption MUST be performed atomically:

1. validate reward exists
2. validate sufficient balance
3. deduct coins
4. create redemption record
5. commit

If any step fails, rollback.

Never trust a coin balance supplied by the frontend.

Return clear errors, especially:
- reward not found → 404
- insufficient balance → 400/409 as appropriate
- invalid request → 422

Prevent race-condition/double-spend issues using appropriate database transaction/locking behavior.

==================================================
4. API QUALITY
==================================================

Keep the existing architecture:

router → service → database/repository layer

Do not put business logic inside route handlers.

Use:
- Pydantic schemas
- typed responses
- proper HTTP status codes
- centralized error handling
- parameter validation

Avoid N+1 queries.

Add indexes if query patterns require them.

Do not introduce unnecessary dependencies.
